# BaiduDiskLink 可写挂载完整实施计划

## 1. 文档状态

| 项目 | 内容 |
| --- | --- |
| 状态 | 规划完成，尚未开发 |
| 目标版本 | 可写挂载版本 |
| 当前基线 | 只读 FUSE、按需读取、SQLite 元数据缓存、可选远端删除 |
| 核心原则 | 百度服务端是最终事实来源，本地元数据和暂存区都不是远端真相 |
| 首要风险 | 上传中断、覆盖数据丢失、FUSE 错误无法反馈、上传抢占播放带宽 |

本文只定义完整方案、开发顺序和验收标准，不包含本轮代码实现。

## 2. 背景与目标

BaiduDiskLink 当前主要面向 DSM 与 Emby 媒体库，通过 FUSE 把百度网盘目录映射为本地路径。现有实现已经支持浏览、播放和可选删除，但不能像普通目录一样接收复制、创建目录、移动或重命名操作。

可写版本的目标是让本机程序、File Station，以及能够正确访问该 FUSE 挂载点的客户端完成以下工作：

- 新建目录。
- 将新文件复制到挂载目录并上传到百度网盘。
- 重命名文件或目录。
- 在挂载范围内移动文件或目录。
- 删除文件或目录。
- 在明确规则下覆盖已有文件。
- 容器或网络中断后恢复未完成的上传任务。

可写功能不能破坏当前已经验证过的 Emby 播放性能和只读稳定性。

## 3. 非目标与限制

| 能力 | 是否支持 | 说明 |
| --- | ---: | --- |
| 新文件上传 | 是 | 使用本地暂存文件，完成后提交远端 |
| 新建目录 | 是 | 调用百度目录创建接口 |
| 重命名、同盘移动 | 是 | 调用百度文件管理接口 |
| 删除 | 是 | 沿用现有远端成功后再更新本地缓存的语义 |
| 覆盖文件 | 是，分阶段 | 必须保证上传失败时旧文件仍然存在 |
| 随机顺序写入新文件 | 是 | `WriteAt` 写入本地暂存文件，最终整文件上传 |
| 修改已有文件中间一段 | 有限支持 | 必须先取得完整旧文件，再生成并上传完整新文件，成本很高 |
| 追加已有远端文件 | 有限支持 | 与修改已有文件相同，需要完整重建 |
| 云端原地块修改 | 否 | 百度上传接口不是远程块设备协议 |
| 硬链接、符号链接、设备文件 | 否 | 百度网盘没有等价语义 |
| 完整 POSIX ACL、xattr、chown | 否 | 只保留本地展示所需的有限属性语义 |
| 实时双向同步 | 否 | 本地是远端视图，不维护两套可独立修改的数据副本 |
| 修复 DSM 自带 Samba 的 FUSE 兼容问题 | 否 | 这是 DSM Samba 与非原生文件系统边界问题，不属于可写层 |

## 4. 一致性原则

可写版本继续采用“远端为准、本地跟随”的模型：

1. 写入中的内容先落到本地暂存区，不直接进入正式元数据表。
2. 暂存文件在上传成功前只能被视为本地待提交对象。
3. 百度服务端确认创建成功后，再刷新远端元数据并更新 SQLite。
4. 上传失败时不伪造远端成功状态，不把待上传对象写成正式远端条目。
5. 删除、移动、重命名均先执行远端操作，成功后再更新本地缓存。
6. 程序重启后根据持久化任务恢复，不通过猜测文件状态完成提交。
7. 目录定时刷新不能删除或覆盖仍处于本地写入状态的临时节点。

### 4.1 可见性语义

为兼容普通文件复制程序，正在写入的文件需要在创建它的挂载会话中立即可见，但必须明确区分两类对象：

| 对象 | 数据来源 | 是否已在百度存在 |
| --- | --- | ---: |
| 远端条目 | SQLite 中的服务端元数据 | 是 |
| 暂存条目 | 上传任务表和本地暂存文件 | 否或尚未确认 |

目录读取时合并这两类条目；同一路径存在待提交任务时，暂存条目优先用于本地写入会话。上传成功后移除暂存条目并用服务端返回的正式条目替换。

## 5. 总体架构

```text
本机程序 / File Station / 可用的 SMB 客户端
                    |
                    v
          FUSE Create / Write / Rename
                    |
                    v
        本地 Staging 文件 + 上传任务表
                    |
                    v
       百度预创建 -> 分片上传 -> 创建合并
                    |
                    v
       查询远端元数据 -> 更新 SQLite 缓存
```

### 5.1 模块边界

| 模块 | 职责 |
| --- | --- |
| `internal/fs` | 实现 FUSE 写操作、句柄生命周期、暂存条目展示和 errno 映射 |
| `internal/upload` | 管理暂存文件、上传任务、重试、恢复、配额和并发 |
| `internal/baidu` | 封装目录创建、预创建、分片上传、合并、移动、重命名等百度接口 |
| `internal/store` | 保存正式元数据和上传任务状态 |
| `internal/remote` | 继续负责读取；上传成功或覆盖后清理相关读取缓存和 dlink 缓存 |
| `internal/app` | 初始化上传管理器、恢复任务并注入 FUSE |
| `internal/config` | 解析可写开关、暂存目录、并发、容量和冲突策略 |

不应把上传逻辑直接塞进当前的 `remote.Reader`。读取和上传具有不同的资源调度、错误语义和生命周期，应保持独立。

## 6. 百度接口设计

开发前需要用官方文档和测试账号确认当前接口参数、错误码及权限范围。计划中的调用链如下：

### 6.1 目录与文件管理

| 操作 | 预期接口语义 |
| --- | --- |
| 新建目录 | 创建接口，`isdir=1` |
| 重命名 | `filemanager` 的 rename 操作 |
| 移动 | `filemanager` 的 move 操作 |
| 删除 | 现有 `filemanager` delete 操作 |
| 查询提交结果 | `stat` 或目录列表接口 |

### 6.2 文件上传

标准大文件上传流程：

1. 根据百度要求切分本地文件并计算分片 MD5。
2. 调用预创建接口，提交目标路径、大小、分片列表和冲突策略。
3. 保存服务端返回的 `uploadid` 和实际需要上传的分片序号。
4. 将缺失分片上传到分片上传接口。
5. 调用创建接口合并文件。
6. 查询最终文件元数据，确认路径、大小和服务端标识。
7. 更新 SQLite，清理上传任务和暂存文件。

接口层建议增加独立能力，而不是无限扩充现有只读 `Client`：

```go
type WriteClient interface {
    CreateDirectory(ctx context.Context, path string) (RemoteEntry, error)
    Precreate(ctx context.Context, request PrecreateRequest) (PrecreateResult, error)
    UploadPart(ctx context.Context, request UploadPartRequest) error
    CommitUpload(ctx context.Context, request CommitUploadRequest) (RemoteEntry, error)
    Rename(ctx context.Context, from, newName string) error
    Move(ctx context.Context, from, targetDir string) error
}
```

具体类型以官方接口验证结果为准，接口中不能泄漏 HTTP 表单细节到 FUSE 层。

## 7. 本地暂存与任务模型

### 7.1 目录布局

建议将暂存区放在持久化 `/data` 下，并确保它不位于 FUSE 挂载目录内部：

```text
/data/uploads/
  staging/
  failed/
```

暂存文件使用任务 ID 命名，不直接使用用户文件名，避免路径转义、重名和特殊字符问题。原始远端路径只保存在任务表中。

### 7.2 上传任务表

建议增加 `upload_tasks` 表：

| 字段 | 用途 |
| --- | --- |
| `task_id` | 本地唯一任务标识 |
| `remote_path` | 最终远端路径 |
| `parent_path` | 父目录路径 |
| `display_name` | 挂载点显示名称 |
| `staging_path` | 暂存文件绝对路径 |
| `size` | 当前逻辑文件大小 |
| `state` | 任务状态 |
| `upload_id` | 百度上传会话标识 |
| `block_list` | 分片 MD5 和状态，使用 JSON |
| `conflict_policy` | 冲突处理策略 |
| `attempts` | 已重试次数 |
| `last_error` | 最近失败原因 |
| `created_at` | 创建时间 |
| `updated_at` | 最近更新时间 |

任务状态建议固定为：

```text
writing -> queued -> hashing -> precreating -> uploading -> committing -> committed
                                           \-> failed
```

任何状态迁移都应先持久化，再执行下一步外部操作。`committed` 只有在服务端查询确认后才能写入。

### 7.3 空间管理

- 创建和扩展暂存文件前检查可用空间与配置上限。
- 超过上限时返回 `ENOSPC`。
- 已失败任务默认保留，便于重试和诊断。
- 不自动删除用户数据；后续提供显式清理命令，将文件移入回收或隔离位置。
- 暂存空间统计必须包含 writing、queued、uploading 和 failed 状态。

## 8. FUSE 写入语义

### 8.1 需要实现的操作

| FUSE 操作 | 计划行为 |
| --- | --- |
| `Create` | 校验写开关与路径，创建任务和暂存文件，返回可写句柄 |
| `Mkdir` | 远端创建成功后刷新父目录 |
| `Open` | 按 flags 区分只读、新文件、覆盖和追加 |
| `Write` | 使用 `WriteAt` 写本地暂存文件，支持乱序和重复写 |
| `Setattr` | 支持文件大小变化，即 truncate；其他属性做有限兼容 |
| `Flush` | 提交写入并可靠返回上传错误，保证同一句柄多次 Flush 幂等 |
| `Fsync` | 等待远端提交完成后返回 |
| `Release` | 释放句柄和引用；不能作为唯一错误反馈点 |
| `Rename` | 暂存对象更新任务路径；远端对象调用远端重命名或移动 |
| `Unlink/Rmdir` | 沿用远端成功后更新本地缓存的现有逻辑 |

### 8.2 写句柄状态

每个可写句柄至少保存：

- 任务 ID。
- 暂存文件句柄。
- 当前逻辑大小。
- 是否发生写入。
- 是否已请求提交。
- 提交结果和错误。
- 打开 flags。
- 句柄引用计数或共享任务引用。

同一路径首版只允许一个活跃写任务。第二个冲突写入返回 `EBUSY`，避免静默合并不同进程的写入。

### 8.3 Flush、Fsync 与 Release

不能只依赖 `Release` 上传，因为很多应用不会可靠展示关闭文件时的错误：

- `Flush`：首次调用触发提交并等待结果；重复调用返回同一结果。
- `Fsync`：确保当前内容已成功提交到百度服务端。
- `Release`：只做资源释放；若应用从未调用 Flush，可触发提交，但日志必须记录无法反馈给调用方的失败。
- 上传过程中继续 Write：首版返回 `EBUSY`，不允许修改正在提交的暂存文件。

## 9. 新文件上传流程

```text
Create
  -> 创建 writing 任务和 staging 文件
Write/Setattr
  -> 更新本地文件和任务大小
Flush/Fsync
  -> 冻结写入
  -> queued
  -> hashing
  -> precreating
  -> uploading
  -> committing
  -> 服务端 Stat 确认
  -> 更新正式元数据
  -> 清理读取缓存
  -> committed
```

失败时返回适当 errno，并将任务置为 `failed`。暂存文件保留，以便重试，不向正式远端视图声称上传成功。

## 10. 覆盖与已有文件修改

### 10.1 安全覆盖

禁止使用“先删除旧文件，再上传新文件”的流程。推荐事务近似方案：

1. 新内容上传到同目录的唯一临时远端名称。
2. 查询并确认临时远端文件大小和标识正确。
3. 通过文件管理接口将旧文件移动或重命名为备份名。
4. 将临时文件重命名为目标名称。
5. 成功后删除备份；任一步失败则执行可验证的补偿操作。

如果官方接口不能提供足够可靠的替换语义，首版覆盖功能应关闭，返回 `EEXIST` 或 `EOPNOTSUPP`，不能以数据安全换取表面兼容。

### 10.2 修改已有文件

百度接口不提供块级原地写入。打开已有文件进行写入时必须：

1. 将原文件完整下载到暂存区，或建立能够补齐未修改区间的本地稀疏文件。
2. 应用本地随机写和 truncate。
3. 将最终完整文件按安全覆盖流程重新上传。

这对大型视频代价很高。因此默认只支持覆盖式写入：带 `O_TRUNC` 打开的文件从空暂存文件开始；没有 `O_TRUNC` 的已有文件写入首版返回 `EOPNOTSUPP`。追加和局部修改放在后续阶段。

## 11. 目录创建、移动和重命名

### 11.1 新建目录

- 远端创建成功后刷新父目录。
- 同名目录存在时映射为 `EEXIST`。
- 禁止在挂载根之外创建路径。

### 11.2 重命名和移动

| 情况 | 行为 |
| --- | --- |
| writing/failed 暂存文件 | 更新任务目标路径和本地展示，不调用远端 |
| 已上传文件同目录改名 | 调用远端 rename，成功后刷新父目录 |
| 已上传文件跨目录移动 | 调用远端 move，成功后刷新源、目标目录 |
| 目录移动到自身子目录 | 返回 `EINVAL` |
| 目标已存在 | 默认返回 `EEXIST`，不静默覆盖 |
| 正在上传的任务 | 返回 `EBUSY` |

远端操作成功、本地缓存更新失败时，应立即强制刷新相关目录；不能回滚远端后再假装操作失败。

## 12. 配置方案

建议新增以下配置，默认全部保持当前只读行为：

```dotenv
# 总写入开关。未开启时保持当前行为。
BAIDUDISKLINK_ENABLE_WRITE=

# 可选删除仍使用独立开关，避免开启上传时同时允许删除。
BAIDUDISKLINK_ENABLE_DELETE=

# 持久化暂存目录，不能位于 FUSE 挂载路径内部。
BAIDUDISKLINK_UPLOAD_STAGING_PATH=/data/uploads

# 上传分片并发。默认 2，避免抢占 Emby 下载带宽。
BAIDUDISKLINK_UPLOAD_CONCURRENCY=2

# 暂存区最大总字节数，默认 100 GiB。
BAIDUDISKLINK_UPLOAD_MAX_STAGING_BYTES=107374182400

# 冲突策略：fail 或 rename。首版默认 fail。
BAIDUDISKLINK_UPLOAD_CONFLICT_POLICY=fail
```

配置校验要求：

- 写开关开启时暂存目录必须可创建、可写并持久化。
- 暂存目录不能等于或位于 FUSE 挂载目录之下。
- 并发至少为 1，并设置保守上限。
- 容量上限必须为正数。
- 未开启写开关时，不启动任务恢复和上传 worker。

## 13. 资源调度与播放隔离

上传不能让已稳定的 Emby 播放退化：

- 上传使用独立 HTTP Client 和连接池。
- 下载保持前台优先，不与上传共享全局并发令牌。
- 默认上传并发为 2，且允许配置更低值。
- 上传哈希和分片读取限制内存占用，不把大文件整块读入内存。
- FUSE 前台读取不能等待上传 worker。
- 元数据刷新不因上传任务进行全树扫描，只刷新相关父目录。
- 后续如需带宽限速，应分别配置上传和下载，不使用一个总限速器。

## 14. 错误映射

| 场景 | errno |
| --- | --- |
| 写功能未开启 | `EROFS` |
| 路径或名称已存在 | `EEXIST` |
| 同一路径正在写入或上传 | `EBUSY` |
| 暂存空间不足 | `ENOSPC` |
| 不支持已有文件局部修改 | `EOPNOTSUPP` |
| 路径不存在 | `ENOENT` |
| 文件和目录类型不匹配 | `EISDIR` / `ENOTDIR` |
| 远端鉴权失败且刷新失败 | `EACCES` |
| 网络或百度接口提交失败 | `EIO` |
| 非法移动或越出挂载根 | `EINVAL` / `EPERM` |

日志应包含任务 ID、远端路径、阶段、百度错误码和重试次数，但不能输出 token、client secret、完整上传 URL 或用户文件内容。

## 15. 崩溃恢复与幂等

启动时按任务状态处理：

| 状态 | 恢复动作 |
| --- | --- |
| `writing` | 保留为失败待处理任务，不自动猜测用户是否完成写入 |
| `queued` / `hashing` | 重新计算必要状态后重试 |
| `precreating` / `uploading` | 使用已有 `upload_id` 和分片状态继续；失效则重新预创建 |
| `committing` | 先查询目标路径或临时路径，确认是否已经提交，避免重复创建 |
| `failed` | 保留并提供显式重试命令 |
| `committed` | 核对元数据后清理残留暂存文件 |

所有远端创建、合并和补偿操作都必须设计幂等检查。不能仅因为 HTTP 请求超时就认定远端操作没有发生。

建议后续提供命令：

```text
baidudisklink uploads list
baidudisklink uploads retry <task-id>
baidudisklink uploads inspect <task-id>
baidudisklink uploads cleanup <task-id>
```

清理命令必须显式执行，并遵守“不直接删除用户文件”的原则，将待清理内容移到隔离或回收目录。

## 16. 安全设计

- 写功能默认关闭，升级后不能自动获得写权限。
- 删除功能继续使用独立开关。
- 暂存目录权限限制为容器服务用户可访问。
- 数据库不保存文件内容，只保存路径、状态、分片摘要和错误信息。
- 配置和日志不得泄漏 OAuth token、App Secret、上传 URL。
- 所有目标路径必须规范化并确认位于配置的远端根目录内。
- 禁止通过 `..`、空字节、异常分隔符逃逸挂载根。
- 对百度返回的文件名再次进行路径安全校验。
- 上传前后校验大小；可用时校验 MD5 或服务端摘要。

## 17. 开发阶段与验收标准

### P0：接口调查和契约测试

| 内容 | 验收标准 |
| --- | --- |
| 验证目录创建、预创建、分片上传、合并、移动和重命名 | 记录真实请求和错误码，不包含隐私信息 |
| 确认上传分片大小、数量上限和冲突参数 | 形成接口契约测试夹具 |
| 确认超时后查询提交结果的方法 | 能区分未提交、已提交和状态未知 |

### P1：百度写接口

| 内容 | 验收标准 |
| --- | --- |

## 18. 自动化测试清单

### 单元测试

- 路径规范化和挂载根逃逸防护。
- FUSE flags、errno 和句柄状态机。
- 乱序 Write、重复 Write、truncate 和稀疏区间。
- Flush/Fsync 幂等和 Release 生命周期。
- 上传任务合法及非法状态迁移。
- 暂存容量计算和 `ENOSPC`。
- 分片 MD5、分片边界和最后一片处理。
- 百度请求参数、响应和错误码映射。
- 正式元数据与暂存条目合并展示。
- 上传成功后读取缓存失效。

### 故障注入测试

- 预创建成功后断网。
- 某一分片重复失败。
- 所有分片成功但合并响应超时。
- 合并成功但本地数据库更新失败。
- 覆盖流程每一个远端步骤失败。
- 上传过程中容器退出。
- token 过期并刷新失败。
- 同一路径并发创建、写入、重命名和删除。

### 集成测试

- 使用临时挂载点执行 `cp`、`mkdir`、`mv`、`rm`。
- 上传后通过现有读取链路逐字节或摘要校验。
- 容器镜像内运行完整测试。
- DSM 上验证 File Station 写入和本地命令行写入。
- Windows SMB 只在可访问 FUSE 的独立 Samba 路径上验证；不把 DSM Samba 兼容性作为可写功能本身的通过条件。

## 19. 性能基线

可写功能必须保留现有读取基线：

- 未开启写功能时，读取路径不增加上传相关锁、数据库查询或后台任务。
- 开启写功能但没有上传任务时，`bench` 和 `bench-fuse` 不应出现可测量的明显下降。
- 上传进行时，Emby 连续播放和 seek 保持稳定；上传可降速，播放不能被上传阻塞。
- 上传使用流式分片，内存占用应近似“并发数 × 分片大小”，不能随文件总大小增长。

真实 DSM 验收应记录修改前后的 `bench`、`bench-fuse`、大视频播放和 seek 结果。

## 20. 发布与回滚

### 发布策略

1. 默认关闭 `BAIDUDISKLINK_ENABLE_WRITE`。
2. 首次发布标记为实验功能，只建议在专用测试目录启用。
3. 先开放新建目录和上传新文件，再开放移动、重命名和覆盖。
4. 每个阶段都保留只读模式作为稳定基线。

### 回滚策略

- 关闭写开关后继续以只读方式挂载，未完成任务仍保留在 `/data/uploads`。
- 数据库迁移必须向前兼容；旧版本忽略新增任务表仍可读取正式元数据。
- 不通过回滚代码自动清理暂存文件。
- 远端已完成的操作以百度服务端结果为准，重启后通过目录刷新重新建立本地视图。

## 21. 最终完成定义

完整可写支持只有同时满足以下条件才算完成：

- 新建目录、上传新文件、移动、重命名、删除和安全覆盖均可用。
- 上传失败、网络中断和容器重启不会损坏原有远端文件。
- 本地暂存任务可观察、可重试、可恢复。
- 正式 SQLite 元数据始终以百度服务端确认结果为准。
- 默认升级后仍为只读，不扩大现有用户的数据风险。
- 自动化测试、故障注入和 DSM 实机测试全部通过。
- Emby 播放和 FUSE 读取性能不低于开发前基线。

## 22. 推荐实施顺序

建议严格按照以下顺序开发，不跨阶段提前开启高风险能力：

1. P0 接口调查。
2. P1 百度写接口。
3. P2 暂存与持久化任务。
4. P3 新文件和目录。
5. P4 移动与重命名。
6. P5 安全覆盖。
7. P6 恢复、运维和文档。
8. P7 DSM 与 Emby 完整回归。

其中 P3 完成后即可形成第一个可试用版本；P5 通过前，不应宣称支持安全覆盖已有文件。
